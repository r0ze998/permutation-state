## この報告の数字の見方

数字には、4種類のしるしを付けています。

- **【実測】** 本物のプログラムを動かして測った値です。
- **【シミュレーション】** ルールは本物のプログラムです。ただし、プレイヤーの遊び方は仮定です。
- **【計算】** 仮定の数字を使って、計算で出した値です。
- **【見積もり】** 予想です。いちばん不確かな数字です。

### (a) 計算量の測り直し：達成

**言葉の説明**
- **CU** は、Solana で処理にかかる「計算量」の単位です。1回の処理には上限があります。
- **SBPF v2** は、Solana のプログラムの新しい形式です。暗号の計算が約2〜3倍速くなります。

**結果**
- 乱数の確認（drand）は、約33万 CU でできました。古い形式では約89万 CU でした【実測】。
- 戦闘1回の計算は、最悪で約63万 CU でした【実測】。
  - 前の見込み（約27万）の**約2.3倍**です。前の数字は、仮のルールで測っていたためです。
  - そのため、無理なく遊べる人数は**約5万人**に下がりました【計算】。
  - M1 で、重い部分（戦場を押さえる処理と、ぶつかり合いの計算）を軽くします。
- ずるい封（あとで説明）の証明は、約4.8万 CU でできました【実測】。
- 次の2つも、実験用のプログラムで確かめました【実測】。
  - 「先にお金を送りつけて、記録を作れなくする」いたずらが効かないこと。
  - 「同じ記録を2つ作る」ことができないこと。
- **まだ測れていないもの：** 「到着の公開（Reveal）」の処理の全体です。この処理はまだ作っていません。M1 で作って測ります。この数字は、下の (c) にも関係します。

### (c) 手数料を使った妨害（C4）：一部達成

**どんな攻撃か**
- Solana では、手数料を多く払った取引が先に処理されます。
- 悪い人は、大量の取引で1つの時間帯を埋めることができます。そうすると、相手の「到着の公開」を締め切りまで通さないようにできます。
- 公開が間に合わなかった軍は、兵の半分を失います。

**合格条件（C4）**
- 「ある勢力の、ある時間帯の戦い全部を止めるための費用が、その戦いの価値の10倍以上であること」です。

**言葉の説明**
- **チップ**は、公開の取引に付ける追加の手数料です。初期設定は1回1万 lamports、約0.15セントです。
- **キーパー**は、プレイヤーの代わりに公開の取引を送ってくれる手伝いのプログラムです。
- **支払い口座**は、取引の手数料を払う口座です。

**実験でわかったこと【実測】**
- 自分のパソコンに Solana の試験用ネットワークを立てて、攻撃を再現しました。
- 本物の Solana と同じ上限が働くことを確かめました。
  - 1つの記録には、1ブロックあたり約4,000万 CU までです。
  - 1ブロック全体では約1億 CU までです。
- 攻撃する側より手数料が低い取引は、全部止められました。
- 手数料で上回れば、1〜2秒で通りました。
- **新しくわかった弱点：** 攻撃者は、キーパーの支払い口座を安く止められます。
  - 1つの口座を約11秒止められました。
  - 20個の口座を、1本の攻撃でまとめて止められました。
  - 新しい口座に変えると、0.9秒で通りました。
  - そのため、キーパーは**150個以上の口座を順番に使う**ことにしました。

**計算の結果【計算】**
- 初期のチップだけの場合：止める費用は1回の時間帯（10分）で約1,400〜14,000ドルです。**いちばん厳しい価値の数え方では、10倍に届きません（未達）。**
- 防衛用の積立を使い、150個以上の口座で送る場合：止める費用は約26,500〜67,400ドルです。**どの数え方でも10倍以上（12〜540倍）です（達成）。**
  - 防衛用の積立とは、攻撃されたときだけ、キーパーが手数料を上乗せできるように運営が用意しておくお金です。

**「一部達成」とした理由**
1. **合格の条件をずらしています。** オーナーが決めた O7 では、「初期のチップで」達成することになっていました。改訂3.1 では、「防衛用の積立を使って」達成することに直しました。この直し方でよいか、オーナーの確認が必要です（6章 N1）。
2. **戦いの「価値」の数え方を、まだ決めていただいていません（D25）。** 3つの案があります。どれを選んでも、積立を使えば計算の上では達成します。
3. **達成の根拠になる仕組みは、まだ設計だけです。** 防衛用の積立、150個の口座、キーパーのルールは、まだ作っていません。
4. **自分のパソコンでは確かめられないことがあります。** 本物の Solana にしかない、取引をまとめて先に通す仕組み（Jito）などです。最終判断は M4 の試験です。M4 では本番に近い環境を使います。そのため、一つ一つの手順にオーナーの承認が必要です。

**達成している部分**
- 「乱数の候補から都合のよいものを選ぶ」ことはできません【実測、実験用プログラム】。
- 乱数の記録を止められても、ゲームが遅れるだけです。結果は変わりません。

### (d) 大きい勢力に人が集まりすぎないこと：達成（シミュレーションで）

- 勢力の大きさが3倍でも、大きい勢力にいる人のほうが得をしないようにしました。
  - 1 USDC あたりの受け取りは、小さい勢力の約0.68倍になります【シミュレーション】。
- 割引の強さは γ = 0.6 です（決定 O6）。
- **注意：** シミュレーションのプレイヤーは、仲間と協力しません。本物のプレイヤーは協力するので、結果が変わるかもしれません。M3 で、人が遊んだ結果で測り直します。

### (e) ルールのテスト：一部達成

- 大事なテストは通っています【実測】。
  - 到着の順番が変わっても、枠に入る軍が同じになること。
  - 公開の締め切りより後に、乱数が決まること。
  - 遅れて処理しても、結果が同じになること。
- ルールのテストは354個あり、全部通りました。この報告のために自分で動かして確かめました【実測】。
- **まだのもの：** 「数の上限のチェック」です。たとえば、兵の数や戦闘の倍率が、決まった上限を超える入力を断る処理です。まだ入っていないことを、コードで確かめました。約2日で入れられます【見積もり】。

## 3. 2回目の作業でわかったこと（まとめ）

**確かになったこと**
- drand の乱数は、Solana の上で確認できます【実測】。
- ずるい封は、チェーンの上で証明できます【実測】。
  - **封**とは、行き先を時間が来るまで誰にも読めないようにする暗号です。
  - わざと壊れた封を出した軍は、証明されると全部失います。
- 役職のお金には上限を付けました。役職のお金を足しても、受け取りは自分が払った額の95%までです。役職で得はしません。
- ボットは、いちばん得な参加日を選んでも、払った額より少なくしか受け取れません。いちばん得な場合でも0.98倍です【シミュレーション】。
- お金の合計が合わなくなることは、どの実験でもありませんでした【シミュレーション】。

**新しく見つかった問題**
- 戦闘の計算が、思ったより約2.3倍重いことがわかりました【実測】。無理なく遊べる人数は、約5万人に下がりました【計算】。
- 初期のチップだけでは、手数料の妨害に負けることがあります【計算】。
- **ボットが役職の多くを取ります。** ボットが全体の1%でも、役職の約6割を取ります【シミュレーション】。
- **ボットの役人が「指令」を操作すると、ボットが得をします。**
  - たとえば、ずっとオンラインでないとできない指令ばかりを選ぶ場合です。
  - このとき、ボットは払った額の約1.04倍を受け取ります【シミュレーション】。
  - 対策は「指令は決まった種類だけにする」ことです。これは設計上の対策で、シミュレーションではまだ確かめていません。M3 で確かめます。
- 後から賭け金を払う人の受け取りが、10〜18ポイント下がりました【シミュレーション】。ボット対策の副作用です。やわらげる案が D22 です。
- しばらく誰も触らなかった州を動かすとき、「誰も来なかった」ことの証明が必要です。1日ぶりだと最大144回分で、費用は約0.1ドルです【計算】。M1 で、もっと安い方法を決めます。

## 4. M0 を終えるために残っている作業

合計で**約5〜6日**です【見積もり】。

1. **数の上限のチェック**を、ルールのプログラムに入れます（約2日）。
2. **点検で見つかった、プログラムの細かい問題**を直します（約1日）。例：
   - 役職の上限の設定に、100%を超える値を入れられてしまいます。100%を超えると、役職で得をできてしまいます。
   - 賭け金の値段の計算が、少し重いです。
3. **設計書の細かい直し**をします（約1日）。例：
   - 乱数を決める時刻の書き方を、プログラムと同じ「切り上げ」にそろえます。
   - 公開のチップの最低額を決めます。
   - 運営が、シーズンの地形の乱数を引き直せないようにします。
4. **実験の細かい直し**をします（約1日）。例：
   - **防衛用の積立の大きさを見直します。** 今は「1回の攻撃で最大0.02 SOL」としています。でも、戦争中は、公開以外の取引にも上乗せが必要です。そのため、1回あたり1〜2 SOL かかりそうです【計算】。
5. **オーナーの承認をいただいたら、コードを GitHub に送ります。** そこで公開の自動テストを動かします。

## 6. 次の段階（M1「最初の鐘」）で作るもの

**期間：** 約8週間です【見積もり】。本番の第1シーズンは、作業開始から**約8か月半後**の予定のままです【見積もり】。
**M1 のテストまでは、遊べるゲームはありません。** 短期戦をやめたためです（決定 O8）。

**作るもの（お金はまだ使いません）**
- Solana 本体で動く、ゲームのプログラムです。
  - 参加する、村を持つ、兵を集める、建てる。
  - 秘密の進軍（封は必須）と、到着の公開。
  - 鐘ごとの戦い、ずるい封の証明、探索、地図の広がり。
  - drand の乱数を記録するしくみ。
- キーパー（代わりに公開するプログラム）。攻撃されたら手数料を上げます。支払い口座は150個以上を順番に使います。
- たくさんの人が地図を見られる配信の仕組み。今のサーバーは、500〜1,000人で止まります。
- 画面：地図、村の画面、進軍の画面、新人向けの案内、練習モード。

**M1 の合格条件**
- 全部の処理が、計算量の上限の中に入ること。
- いたずら（お金の送りつけ、記録のにせもの）へのテストが、全部の作成手順にあること。
- 1,000体のボットで7日間のシーズンを、手元で最後まで動かせること。
- **そのあと、オーナーの承認をいただければ、** 50〜200人の非公開テストをします（お金なし）。

**M1 で測って決めること**
- 「到着の公開」の計算量。C4 の計算に使います。
- 誰も来なかったことの、安い証明のしかた。
- 戦闘の計算を軽くすること。

**M1 で気をつけること**
- 作る量が多いです。
- 戦闘の計算がこれ以上重くなると、上限に近づきます。
- 新しい仕組みを入れるたびに、勢力の釣り合いがずれます。そのたびに測り直します。
