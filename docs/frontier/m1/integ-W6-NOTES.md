## 3. The one gate finding: criterion 3's close → resolve target

The Gate W6 latency line (`up --mode accel --beacon test-key --scale 2 --game-hours 6 --bots 300 --run-id w6-latency --base-port 41000 --chaos`, on `b1044b4`, 12,165 s of wall time: 36 play bells at 2× and the drain at 20×) made marches this time (W6-A's own run had none): 25 departs, 23 Reveals, 23 CLASH records. The report at `b1044b4` read **close → resolve p50 64 / p99 65 game s** against the 60 s target and exited 1 (so the line's `down` did not run and the stack stayed up until this session).

The number is the program's, not the keeper's: ResolveFromInputs needs the seed of THE anchor, `S(b, r) = first_round_from(close + Δ)` with `Δ = seed_margin ≥ 60` (§5.1; `SeasonParams` validation refuses less), public one drand delay (1 s) later; the cache then lands in 2 slots and the resolve in 1–2 (at 2× a slot is 0.8 game s: p50 80 slots = 61 s ÷ 0.8 + 2 + 1.75). The keeper gathers at `now ≥ close` (`keeper::play::clashes`) and can do nothing sooner. A "close → resolve ≤ 60 s" reading cannot pass with any keeper, and at 20× the 8-slot reading from the close would fail the same way (8 slots = 64 game s < Δ + delay + landings).

Fix (`7b9995f`, `crates/stack/src/report.rs`, W6-A's path, integration window): `s_to_resolve_slots` / `s_to_resolve_game_secs` measured the way W6-A pinned round → anchor (W5-B F5): slots from the first slot whose Clock shows `S(b, r)` public, game seconds from the publication instant, to the CLASH landing; criterion 3 judges the close → resolve target on it and prints close → resolve next to it. Re-run of the line's `report && down` (the run itself unchanged; the report reads the run's transactions): **criterion 3 pass** — round → anchor 2.0 game s, S → first cache 2.0 s, anchor → last reveal 0 s, **S → resolve p50 3 / p99 4 slots = 3 game s** (targets 5 / 5 / 30 / 60 s), close → resolve 65 s reported; idle province-days ≤ 3 SkipQuiet (19 days), churned up to 18 (18 days, 10 over 6; reported). Contract §13.4 criterion 3 amended in place (v1.10) and §26; DECISIONS Q3 says why this is not a hidden bug.

For the main session's 7-day run: at 20× the report will judge S → resolve ≤ 8 slots; the keeper's 3–4 slots leave headroom. The other latency figures of the run, all pass: see `runs/integ-w6-latency/report.md`.
